#### Correctness and security

**R-1 · Unauthenticated `deleteUser` on both surfaces (EC-20).** `delete-user.resolver.ts` and `delete-user.route.ts` resolve no session or organization context, and the only global hook (`request-context.ts`) sets a request id. Story 2.1 (`2b9df8f`) *added* the GraphQL resolver to satisfy the parity contract, widening the pre-existing REST exposure. Re-checked: the delete targets the boilerplate `users` demo table (`user.repository.ts:22`), not Better Auth's `"user"`, so no identity can be erased. It remains an unauthenticated destructive endpoint. *Instance:* fix now by deleting the boilerplate `user` and `settings` modules and the `users` table (a drop migration). *Prevention:* lesson P3.

**R-2 · Concurrent transitions can break "resolved is terminal" (AD-1, EC-1, EC-2, EC claim on 2.9).** `findById` is a plain `select` (`incident.repository.ts`) and `updateStatus` writes `where id = …` with no status predicate. Under READ COMMITTED, two transitions of one incident can both pass `assertTransition` against the same `from`. `identified → resolved` and `identified → monitoring` together can leave a resolved incident reopened with `resolved_at` set, two contradictory timeline entries, and both events emitted. The handler's comment "the status cannot move underneath the check" is false. *Instance:* fix now. Use `select … for update` in the transition read, or `update … where status = ${from}` with a conflict on no row, plus a concurrent-transition test. *Prevention:* lesson P5.

**R-3 · Posted updates can record a stale status (AD-2).** `post-incident-update` reads status with the same unlocked `findById`, so it can record the pre-transition status. *Instance:* fix now, with R-2 (`for share`).

**R-4 · Event bus does not isolate handlers (AD-12, EC-17).** `emit` calls each handler in a bare loop (`event-bus.ts:39–47`). A synchronous throw skips sibling handlers and returns 500 from a command that has already committed. A rejected promise from an unguarded handler is unhandled and can crash the process. Only the recompute handler guards itself today. *Instance:* fix now, before Epic 4 adds the NOTIFY bridge as a second subscriber.

**R-5 · Public subscribers never hear about `identified` or `monitoring` (EC-3, AD-19).** In `DOMAIN.md`'s catalog, `incident.state_changed` is **Admin-only** (line 1195), while `incident.resolved` and `incident.confirmed` are Public. DOMAIN's original IncidentUpdate invariant covered this gap: "every public lifecycle transition appends an update and emits `incident.update_posted`". The remediation `87259e6` added a contradicting rule, "only a posted update is announced as `incident.update_posted`", in the same section, and implemented it. The contradiction is re-checked: both lines are present. **This was the retrospective author's own error in the remediation:** it traded a double announcement for no public announcement at all. *Instance:* fix now, pending the human decision in Open questions. *Prevention:* lesson P6.

**R-6 · Worker robustness.** All re-checked:
- Tenant discovery runs outside the per-organization `try`. `await listOrganizationIds()` sits in the `for` header (`worker.ts`), so a database outage makes the `void`-called pass reject unhandled and can crash the worker (EC-14).
- `setInterval` has no in-flight guard, so passes can overlap, and `WORKER_MAINTENANCE_INTERVAL_MS` has no minimum (`env.ts:37`) (AD-6, EC-15).
- Shutdown awaits neither the in-flight pass nor `drain()`, in the worker or the API (AV-10, VG-5, AD-5, EC-16).
- The worker and seed build with `logger: false`, and the DI logger is `fastify.log` (`di/index.ts:12`). Recompute failures in the worker therefore log nowhere, contrary to the handler's claim (EC claim).

*Instance:* fix now, as one change.

**R-7 · No self-healing after a failed recompute (AD-4).** A recompute that fails is logged and dropped, and its trigger is one-shot. DOMAIN defers a reconciliation pass to post-v1 (its "known risk" covers missed emits, not failed handlers). *Instance:* fix now as a spec change: recompute every organization at the end of each worker pass. It is idempotent and silent when nothing moved. DOMAIN's known-risk paragraph changes first.

**R-8 · Maintenance edits and deletes exceed the stories' scope (AD-7, AD-8, AD-9, EC-12, EC-13, EC claims on 2.14 and 2.15).**
- `remove()` deletes a window in any status, but story 2.14 and the route say deletion is "for work that never happened".
- `update` has no status guard, but story 2.12 scopes edits to scheduled windows and the route says "Change a scheduled maintenance window".
- `completeDue` stamps `started_at` on a scheduled window completed without ever starting, which the manual path does not do.

Story 2.17 then *relied* on the unguarded paths: its DOMAIN amendment and test delete an in-progress window, and it added `maintenance.updated` as a trigger for editing one. *Instance:* fix now, pending the human decision in Open questions. The 2.17 delete test becomes a completion test, which also closes VG-1.

**R-9 · Input handling that returns 500 instead of 400.** All re-checked:
- GraphQL date strings are passed to `new Date()` unvalidated, and `assertWindow` lets `NaN` through (`end <= start` is false for `NaN`) (AD-17, EC-10, EC-11).
- An explicit GraphQL `null` for `affectedServices`, `affectedServiceIds` or `title` passes `!== undefined` checks. The nullable SDL lists crash on `.length`, and not-null columns raise 23502 (EC-6, EC-7).
- Duplicate service ids in an affected list raise an unmapped 23505. Only 23503 is mapped and no schema has `uniqueItems` (AD-16, EC-8).
- Service *insert* maps only unique violations, so a foreign or unknown group is a 500 (EC-9).
- Posting a blank or whitespace update is accepted over GraphQL (`String!`) and REST (`minLength: 1`), unlike declare and transition since `87259e6` (AD-14, EC-5).

*Instance:* fix now.
