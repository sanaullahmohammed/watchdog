### Diff-scope review (cross-story)

**DR-1 · Medium · A malformed id on three GraphQL reads is a masked 500, while REST answers 400.** Reproduced on the running stack: `service(id:"x")`, `maintenanceWindow(id:"x")` and `incidentTimeline(id:"x")` each answer HTTP 500 "Internal Server Error". `serviceGroup(id:"x")` answers 400 "Invalid input. id: must match format \"uuid\"". The cause is in the three handlers listed in AV-4. Their REST routes refuse with `format: 'uuid'` (`get-service.route.ts:18`, `get-maintenance.route.ts:18`, `get-incident-timeline.route.ts:20`). This works against the epic's headline, "GraphQL refuses what REST refuses", even though the stories scoped that to mutations. `deferred-work.md` names `service` (#6) and `incidentTimeline` (#16) but not `maintenanceWindow`. `graphql-error-formatter.integration.test.ts:163` pins the masked 500 as expected and must change with the fix. Boundary: 9.1/9.3/9.4 (mutations) against 9.6/9.7 (new reads). *Instance:* fix before acceptance (action item 1). *Prevention:* 9.11's registry pattern applied to `Query` fields, so a read added without a malformed-id case fails.

**DR-2 · Medium · The worker reports healthy while its database is down.** `runWorkerPass` catches a failed tenant discovery and returns (`src/worker.ts:44-52`). It also catches each organization's failure (`:89`). `startLoop` then records the pass as completed, so the health check passes while no work is done. The epic's goal says "the worker's health says whether it is working" (`epics.md:1086`), and NFR29's line reads "Each healthcheck fails when its process stops doing its work". Story 9.10's acceptance criteria covered a pass that never settles, and that case is met (`worker-health.integration.test.ts:126`). Its "every pass rejects" test (`:175`) injects a rejecting pass, but the real `runWorkerPass` never rejects. Spec 9.10 made this choice deliberately and deferred it (deferred #33). Epic 5 puts the monitor checks in this worker, so the gap grows with them. *Instance:* fix before acceptance (action item 2). *Prevention:* a health criterion is tested against the real pass, not only an injected one.

**DR-3 · Medium · Two app instances open in one process break the second.** Deferred #10 recorded this as "unverified". It is now reproduced. A scratch script built two apps with `buildApp()` and fetched `/status/<slug>` from each. The first answered 200. The second answered 500, and the log said `Command type of status_page/page.get is not registered`. The cause: handlers are awilix `Lifetime.SINGLETON`s in the process-wide `diContainer` (`src/server/di/index.ts:2,29,45`). Their `init()` registers on the bus of the app that first resolved them, while each app gets fresh buses (`src/shared/cqrs/index.ts:26-33`). Two tests already hold two apps open, but neither reads through the second one (`auth-pool-shutdown.integration.test.ts:26`, `public-surface-bounds.integration.test.ts:202`). Deferred #25, making `register` throw on a duplicate, interacts with this. *Instance:* fix before acceptance, by the owner's decision (action item 3). *Prevention:* the fix's test builds two apps and reads through the second.

**DR-4 · Low · Worker shutdown has no error handling.** `src/worker.ts:208-209` runs `await app.close(); await closeDbConnection();` inside `void shutdown(...)`. If `app.close()` rejects, the pool is never ended and the rejection is unhandled. `src/api.ts:25-33` got a try/catch for this in 9.9. Boundary: 9.9/9.10. *Instance:* fix together with action item 2, which is the same file.

**DR-5 · Low, latent · Redaction misses a nested cause.** At debug level, postgres.js makes `parameters` enumerable. `ExceptionBase.toJSON` serializes `cause` (`exception-base.ts:52`). Nothing in `src` passes a database error as a cause today. *Instance:* already deferred as #39 (before Epic 6). This adds the `cause` path to that entry.

**DR-6 · Low · The health file stays on disk after shutdown** (`src/worker-health.ts:139-148`). Boot rewrites it before the first pass. *Instance:* accept.
